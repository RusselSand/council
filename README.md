# Spec Council

Локальный инструмент подготовки ТЗ: от брифа до согласованной спецификации.
Работают ввод, нарезка, раскладка по группам и первый шаг потоков — идея группы. Дальше
по цепочке потока (вопросы, варианты, решения, итоги) и «История» — пока заглушки.

- Backend: FastAPI (Python 3.14+, uv) — `backend/spec_council`: ручки в `api/`,
  контракт в `models.py`, данные за `deps.py` (файлы в `.data`, `store.py`).
- Модели совета: `backend/spec_council/pipeline.py` — шаги нарезки, раскладки и поиска идеи,
  `slicing.py`, `grouping.py` и `ideas.py` — проверка ответов, `prompts/*.md` — промпты, `agents.py` — запуск через пакет
  [agent-workers](https://github.com/RusselSand/agent-workers) (зависимость с тегом
  версии в `backend/pyproject.toml`, он же работает в kromka-agent-worker). Одна модель —
  одно подключение к CLI с подпиской (Claude Code, Codex): вход, замер расхода подписки,
  лоток с оплаченными ответами. Команды — `python -m agent_workers status | login | logout
  | pending | collect` из `backend`, подробности в README пакета.
- Frontend: Vite + React + TypeScript — `frontend/src`.
- Надписи: `frontend/src/i18n` — словари `ru.ts` и `en.ts` (i18next). Язык берётся из
  настроек браузера, переключается в шапке и запоминается в localStorage.

Команды ниже даны по одной на строку: так они одинаково работают в bash и в PowerShell.

Секреты и настройки для локальной работы лежат в `.env` в корне репозитория. Он не
коммитится, образец — `.env.example`:
```bash
cp .env.example .env
```
- `AGENT_WORKERS_TOKEN` — токен только на чтение приватного репо agent-workers:
  fine-grained token с правом Contents: Read только на этот репо. Он нужен сборке
  образов: compose берёт его из `.env` и передаёт build secret'ом, в образ токен не
  попадает. Локальному `uv` токен не нужен: доступ он берёт из git, как и `git clone`.
- `COUNCIL_SOL_HOME`, `COUNCIL_FABLE_HOME` — необязательно: другие каталоги учётных
  записей моделей вместо `.accounts/…`, см. «Вход в модели».
- `COUNCIL_DATA` — необязательно: другой каталог советов вместо `.data`, см. «Где хранятся
  советы».

## Вход в модели
Совет работает через CLI с подпиской: Sol — через Codex (подписка ChatGPT), Fable — через
Claude Code (подписка Claude). Каждой модели нужен свой каталог учётной записи: туда CLI
кладёт токены входа. По умолчанию это `.accounts/sol` и `.accounts/fable` в корне
репозитория. `.accounts/` уже в `.gitignore` и `.dockerignore`: в гит и в образы токены не
попадут. Создавать каталоги руками не нужно, их создаёт вход.

Вход — один раз на каждую модель, на хосте, из корня репозитория. Нужны установленные
`codex` и `claude` (`npm i -g @openai/codex`, Claude Code — по инструкции Anthropic) и
браузер:
```bash
uv run --project backend python -m agent_workers login --provider codex --home .accounts/sol
uv run --project backend python -m agent_workers login --provider claude --home .accounts/fable
```
Каждая команда открывает браузер: войдите в аккаунт с подпиской (для Codex — «Sign in with
ChatGPT»). Лимиты подписки общие для всего аккаунта: если войти своим основным, совет будет
тратить то же окно, что и вы. Проверить вход и увидеть расход подписки:
```bash
uv run --project backend python -m agent_workers status --provider codex --home .accounts/sol
uv run --project backend python -m agent_workers status --provider claude --home .accounts/fable
```
После входа модель в совете перестаёт быть «не подключена». Docker монтирует те же
каталоги в контейнер, второй раз входить не нужно. Каталоги в другом месте — пути в `.env`:
`COUNCIL_SOL_HOME`, `COUNCIL_FABLE_HOME` (относительный путь считается от каталога `.env`).
На Linux впишите в `.env` свои `id -u` и `id -g` как `COUNCIL_UID` и `COUNCIL_GID`:
контейнеры пишут в `.accounts`, и под вашим пользователем всё созданное останется вашим.
Без них контейнеры работают под root — так нужно на Windows и macOS, где Docker Desktop
показывает эти каталоги принадлежащими root.
Выйти — та же команда с `logout`. У Gemini подключения пока нет: в agent-workers нет её
провайдера.

## Нарезка
«Нарезать» запускает работу совета в фоне, этап «Нарезка» показывает ход и итог:
1. каждый участник сам по себе режет текст на смысловые фрагменты (`slice.md`);
2. если нарезки разошлись или кто-то видит несколько вариантов, судья выбирает итоговую
   (`slice_judge.md`); границу, которой нет ни у одного участника, судья провести не может;
3. каждый участник размечает фрагменты: idea, question, proposal, constraint, risk
   (`label.md`);
4. фрагменты, где типы разошлись, решает судья (`label_judge.md`).

Судья не видит, какая модель что предложила, и получает варианты в перемешанном порядке.
В промптах доступны `{{input}}` — исходный текст, а также `{{options}}` у судьи нарезки,
`{{fragments}}` у разметки и `{{fragments}}`, `{{label_options}}` у судьи разметки;
тест `tests/test_prompts.py` следит, чтобы шаблоны ждали только это. Ответ модели
проверяется: фрагменты дословны, по порядку и без потерь, типы из пяти. Негодный ответ
или упавшая модель выбывает из шага, остальные идут дальше. Каждый вызов модели ключуется
советом, шагом, моделью и текстом промпта, поэтому повтор после сбоя берёт оплаченные
ответы даром.

## Группы
Когда нарезка готова, карточка «Дальше» на ней предлагает разложить фрагменты по группам:
1. каждый участник сам по себе группирует фрагменты вокруг идей и отмечает связи между
   группами (`structure.md`); общий фрагмент может стоять в нескольких группах;
2. если раскладки разошлись, судья выбирает итоговую (`structure_judge.md`).

Раскладки сравниваются по составу групп и связям, а не по буквам и названиям; у `related`
направления нет. Судья может собрать итог из решений разных вариантов, но каждое место
фрагмента в группе и каждая связь должны быть хоть в одном из них, а то, в чём сошлись все
варианты, судья не меняет. Идеи группы — её фрагменты с типом idea: их считает совет, а не
модель. В промптах доступны `{{fragments}}` — фрагменты с типами (JSON), и
`{{structure_options}}` у судьи. Если после раскладки поменять тип фрагмента, этапы предложат
разложить заново; новая нарезка группы стирает.

Готовые группы можно поправить руками: объединить две («Объединить с…» — остаются буква и
название той, где нажали), вынести отмеченные фрагменты в новую группу («Разделить»),
переименовать щелчком по названию. Буквы при этом не переставляются, у новой группы —
первая свободная. Предложение совета хранится отдельно, и «Вернуть как предложил совет»
отменяет все правки. Каждая правка привязана к раскладке и версии её групп: разложили
заново или поправили в другой вкладке — прежняя правка отклоняется (409), и экран
показывает нынешние группы. Если типы фрагментов поменяли после раскладки, группы не
правятся: новая раскладка всё равно заменила бы правки, так что сначала — разложить заново.

Когда группы устраивают, «Подтвердить» сбоку делает каждую группу потоком: совет переходит в
статус `review`, а экран — на этап «Потоки». Подтверждение подчиняется тем же правилам, что и
правки: подтверждаются группы той раскладки и версии, что на экране, и не устаревшие после
смены типов. Объединение, разделение или откат после подтверждения меняют состав групп и
снимают подтверждение — потоки и найденные идеи сбрасываются, подтверждать нужно заново.
Переименование потоки не трогает. Новая раскладка или нарезка тоже снимают подтверждение;
пока совет ищет идеи потоков, их не запустить и состав групп не поменять (423).

## Потоки
Поток — подтверждённая группа под той же буквой, со своей цепочкой: группа и идея, вопросы,
варианты, решения, итоги. Работает первый шаг — идея:
- если идея записана в тексте (у группы есть фрагменты типа idea), она просто видна, и её
  утверждают как есть;
- если нет, совет ищет её сразу при подтверждении групп, у всех таких групп разом:
  1. каждый участник сам по себе восстанавливает идею по фрагментам группы
     (`idea_discovery.md`) — один вариант, несколько или ни одного, если честно не видит;
  2. если различных вариантов несколько, судья выбирает или аккуратно сводит их
     (`idea_judge.md`); один вариант — судья не нужен.

Человек видит предложение совета в поле, остальные варианты — с пояснениями и тем, кто их
предложил; может взять любой, поправить формулировку или написать свою. Если никто не
предложил идею или судья не принял ни один вариант, поле пустое, а причина видна. «Утвердить
идею» записывает её в поток (`streams[].idea`, с пометкой, чья она: из текста, совета или
человека) и открывает шаг «Вопросы». Утвердить заново — поменять идею.

Модели видят только фрагменты группы с типами, без её названия; опора идеи — номера
фрагментов группы, вариант с чужим номером отбрасывается. В промптах доступны `{{group}}` —
фрагменты группы (JSON), и `{{idea_options}}` у судьи. Нет подключения к моделям — группы всё
равно подтверждаются, а поиск записан упавшим с причиной: «Запустить снова» на странице
потока.

## Где хранятся советы
Каждый совет со всеми этапами — текст, нарезка, группы, потоки — лежит отдельным файлом
`<id>.json` в `.data` в корне репозитория (другой каталог — `COUNCIL_DATA` в `.env`,
относительный путь считается от каталога `.env`). Сами советы в `.gitignore` и `.dockerignore`,
докер монтирует каталог в контейнер, так что они переживают перезапуск, пересборку и hot reload.

Каталог `.data` лежит в репозитории пустым (`.gitkeep`), и docker его не создаёт: на Linux
созданный им каталог принадлежал бы root, а бэкенд под `COUNCIL_UID` не смог бы в него
писать. Свой каталог в `COUNCIL_DATA` создайте заранее от своего имени, иначе на Linux
`docker compose up` скажет, что его нет (Docker Desktop на Windows и macOS создаст его сам —
там владелец не важен). Если писать в каталог всё же нельзя, бэкенд не запустится и в логе
объяснит почему.
Бэкенд читает каталог при старте, дальше держит советы в памяти и записывает каждую правку
сразу: через временный файл, так что процесс, оборванный посреди записи, совет не испортит
(от пропадания питания это не страхует). Работать с каталогом должен один процесс — второй не
увидит чужих правок.

Ходы моделей, которые шли, когда сервер остановили, при следующем старте помечаются
упавшими: «прерван: сервер остановился». Их можно запустить снова, и ответы, за которые уже
заплачено, возьмутся из лотка даром. Файл, который не читается (правили руками), пропускается
с предупреждением в логе и остаётся на месте. Удалить совет — удалить его файл при
остановленном бэкенде.

## Разработка в докере
Кроме самого докера и `.env` выше, ничего ставить не нужно. Оба сервиса с hot reload.
```bash
docker compose up --build
```
Фронт — http://localhost:5420, API — http://localhost:8420.

После правок `package.json` или `pyproject.toml` пересоберите образы и обновите
анонимные тома (в них лежит `node_modules`):
```bash
docker compose up --build -V
```

## Разработка без докера
Две консоли. `uv` сам поставит зависимости и при необходимости скачает Python 3.14
(версия задана в `backend/.python-version`).
```bash
cd backend
uv run uvicorn spec_council.app:app --reload --port 8420
```
```bash
cd frontend
npm i
npm run dev
```
Фронт на http://localhost:5420, запросы `/api` проксирует на бэкенд.

## Один процесс
Фронт собирается в `frontend/dist`, и дальше его отдаёт сам FastAPI — включая прямые
ссылки на страницы вроде `/councils/demo-1/brief`.
```bash
docker compose --profile prod up app --build
```
Открывается на http://localhost:8080. То же самое локально, на http://localhost:8420:
```bash
cd frontend
npm run build
cd ../backend
uv run uvicorn spec_council.app:app --port 8420
```
